Pawl under real load: how often do we hit rate limits?

The question: under real human use of the go key, how many requests per minute does Pawl send to OpenRouter, which limits does it hit (requests per minute, requests per day, credit budget, provider slowdown), and what are the minimum limits Pawl needs so a user never sees ! rate limit?

This page simulates people pressing the go key and runs each press through Pawl's current request rules: a new press cancels the one in flight, there is no retry after a rate limit, the whole file goes in the prompt. The latency and concurrency numbers come from real requests made with your OpenRouter key on 2026-11-09 (see Where the numbers come from at the bottom). Same settings give the same result every time, so you can change one thing and compare.

Where the numbers come from

Measured with prototypes/rate-limits/probe.mjs against your key, same request shape as src/core/session.ts:

  • Your key has no request-rate limit (GET /api/v1/key → rate_limit.requests: -1) and a $50/week credit limit. OpenRouter docs: paid models have "no platform-level request cap"; limits are per account, not per key.
  • Level 1 (DeepSeek V4.1 Flash, about 3.6k-token file): time to the end of the line p50 640 ms, p90 2.0 s. A 41k-token file: p50 1.7 s. That gives roughly 530 ms + 30 ms per 1k prompt tokens.
  • 25 presses at the same moment: no 429s, but p50 13.6 s. With separate connections, about 5 run in parallel; each one after that waits about 0.7 s more. So too much load shows up as delay, not as a 429.
  • Held go key (60 presses at 30 Hz, each cancels the one before): 60 requests sent, 59 cancelled, no 429s.
  • Kimi K3.1 Pro: p50 1.3 s.
  • Prices ($ per 1M tokens, in/out): Flash 0.051/0.567, Kimi K3.1 Pro 2.00/10.00.

From OpenRouter docs: :free models allow 20 requests/min, and 50/day (under $10 of credits ever bought) or 1000/day ($10 or more). A negative balance gives 402. When a provider sends back 429, OpenRouter first tries other providers.

Assumed (not measured): how often each type of user presses the go key, free-model latency (1.5× Flash), the length of a held key press, and the size of each prompt and reply.
